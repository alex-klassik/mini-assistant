# M15 — само-ревью безопасности перед сдачей

Формальный milestone-отчёт (не чек-лист для повторного прохождения, а
зафиксированный результат разового аудита кода и git-истории репозитория
по трём направлениям из PLAN.md: секреты, логирование ПДн/тела письма,
инъекции через аргументы инструментов).

## 1. Секреты в коде и в git-истории

**Проверено:**
- `grep -i` по коду и `config.example.yaml` на паттерны вида
  `apiKey/secret/password/token/Bearer = "..."` — совпадений нет.
- `git log --all -p` по всей истории репозитория на те же паттерны —
  совпадений нет (секрет не был закоммичен и затем удалён).
- `git ls-files` на файлы с именами вида `.env`/`*secret*`/`*.pem`/`*.key`/
  `*credential*` — таких файлов в индексе нет.
- Прочитаны `LlmConfig.resolveApiKey(EnvProvider)` и
  `AuditConfig.resolveHmacKey(EnvProvider)` — оба читают секрет исключительно
  через переданный `EnvProvider.getenv(name)`, имя переменной берётся из
  конфига (`apiKeyEnv`/`hmacKeyEnv`), нигде нет `System.getenv` в обход этого
  метода и нигде нет захардкоженного значения-заглушки.
- `HttpLlmClient` кладёт `apiKey` только в HTTP-заголовок
  `Authorization: Bearer ...` запроса — ни в одно исключение
  (`LlmClientException`) значение ключа не попадает.

**Вывод:** секретов в коде/истории нет; ключ и HMAC-секрет попадают в
процесс исключительно через переменные окружения, как того требует правило
пользователя №4.

## 2. Логирование тела письма / ПДн

**Проверено:** построчно все точки логирования в `src/main` (`logger.*`,
`System.out`/`System.err`) — их всего 6, в двух классах:

| Файл | Строка | Что логируется |
|---|---|---|
| `AgentService.java` | `logger.warn(... Events.LLM_FAILED, msg.getId(), PiiMasker.mask(e.toString()))` | id письма (Outlook EntryID, не email) + текст исключения после маскировки |
| `AgentService.java` | `logger.warn(... Events.MAIL_SEND_FAILED, msg.getId(), PiiMasker.mask(e.toString()))` | то же |
| `Main.java` | `logger.info("event=agent_started ...")` | только `pollSeconds` из конфига |
| `Main.java` | `logger.info("event=agent_stopped")` | без данных |
| `Main.java` | `logger.error(... PiiMasker.mask(e.toString()))` | текст фатального исключения после маскировки |
| `Main.java` | `System.err.println("Usage: ...")` | статическая строка использования |

Ни один из вызовов не передаёт `msg.getBody()`, `msg.getFrom()` или
`msg.getSubject()` напрямую. `msg.getId()` — это внутренний идентификатор
письма (Outlook `EntryID` в проде, произвольная тестовая строка в тестах),
не email-адрес и не ПДн сам по себе.

Единственный канал, через который в лог теоретически может попасть
что-то из внешнего источника — текст стороннего исключения
(`e.toString()`), например ошибка отправки от почтового сервера, которая
сама содержит email внутри своего сообщения. Для этого случая уже с M10
существует `PiiMasker.mask(...)` — маскирует email-паттерны на `[EMAIL]`
регэкспом `[\w.+-]+@[\w-]+\.[\w.-]+` — и применяется на всех путях, где
логируется `e.toString()`.

Отдельно проверено: `AuditLog.append(String event)` в `AgentService`
вызывается только со строками вида `"event=tool_called tool=" + toolName`
и `"event=mail_processed msgId=" + msg.getId()` — тело письма, отправитель
и результаты выполнения инструментов (включая текст напоминания) в
аудит-журнал не пишутся.

**Вывод:** тело письма, отправитель и тема нигде не логируются и не
попадают в аудит-журнал; единственный риск утечки ПДн (email в тексте
стороннего исключения) закрыт `PiiMasker` на всех точках логирования
исключений.

## 3. Инъекции через аргументы инструментов

**Проверено:**
- `AddReminderTool.execute`/`FindItemsTool.execute` разбирают
  `argsJson` через `ObjectMapper.readTree(...)` (Jackson) — структурный
  парсинг, не `eval`/подстановка в командную строку/SQL; извлечённые поля
  (`text`, `dueIso`, `query`) используются только как значения (аргументы
  метода `ReminderStore.add`/`findByText`), никогда не участвуют в
  построении пути к файлу, команды ОС или динамического запроса.
- `ReminderStore` получает `filePath: Path` **только через конструктор**,
  вызываемый один раз в `Main.buildAgentService`:
  `storePath.resolve("reminders.json")`, где `storePath =
  Paths.get(config.getStore().getPath())` — путь целиком выводится из
  `store.path` конфига (доверенный источник, задаётся оператором при
  установке, не письмом и не аргументом LLM). Ни один метод
  `ReminderStore`/`AddReminderTool`/`FindItemsTool` не принимает путь или
  его часть как параметр — подменить целевой файл через содержимое письма
  или через ответ модели невозможно.
- `findByText` делает `contains(needle.toLowerCase())` — обычный
  подстроковый поиск в памяти по уже загруженному списку объектов
  `Reminder`, не спецсимвол-чувствительный (не regex, не SQL LIKE) —
  инъекция через спецсимволы в `query` не имеет эффекта, кроме как на
  результат самого поиска.
- Некорректный JSON в `argsJson` (например, модель прислала синтаксически
  битую строку, или отсутствует обязательное поле — тогда
  `args.get("text")` вернёт `null` и `.asText()` бросит
  `NullPointerException`) приводит к `RuntimeException`, который перехватывает
  `ToolLoop.executeSafely` (`catch (RuntimeException e)`) и превращает в
  `{"error": "tool '...' failed: ..."}`, возвращаемый **модели** как
  результат tool-вызова — наружу из `ToolLoop.run()` исключение никогда не
  выходит, поэтому такой сценарий не может уронить обработку письма и не
  попадает в логи (в отличие от логирования, здесь адресат сообщения об
  ошибке — сама LLM, а не файл лога, что и так предусмотрено дизайном M5).

**Вывод:** путь к файлу хранилища напоминаний строится исключительно из
конфига и не зависит от содержимого письма или аргументов, которые
присылает модель; аргументы инструментов разбираются безопасным
структурным парсером и используются только как данные, а не как код/путь/
запрос; любой сбой разбора аргументов гасится на уровне `ToolLoop` и не
приводит ни к падению процесса, ни к утечке в лог.

## 4. `.gitignore` и файлы конфигурации

Проверено содержимое `.gitignore` (корень репозитория) и список
отслеживаемых git файлов:

```
target/
*.class
*.log
dependency-reduced-pom.xml
/data/
.env
.idea/ *.iml .vscode/
```

В репозитории закоммичен только `config.example.yaml` (содержит лишь
*имена* переменных окружения — `apiKeyEnv: "LLM_API_KEY"`,
`hmacKeyEnv: "AUDIT_HMAC_KEY"` — без единого реального значения секрета).
Реальный `config.yaml` с боевыми значениями `store.path`/`mail.profile` и
локальные данные приложения (`/data/`: `seen.txt`, `reminders.json`,
`audit.jsonl`) не отслеживаются `.gitignore` под каталог `/data/`, но
конкретно `config.yaml` в `.gitignore` явно не перечислен — сам файл
секретов не содержит (секрет живёт только в переменной окружения, не в
YAML), поэтому случайный коммит `config.yaml` не приведёт к утечке ключа,
но раскроет непубличные операционные детали (`mail.profile`, путь
хранилища). Это не блокирующая находка (наименование окружения — не
секрет), но для аккуратности стоит явно исключить рабочий `config.yaml` из
git.

Проверка по всем трём направлениям, заявленным в PLAN.md для M15, пройдена
