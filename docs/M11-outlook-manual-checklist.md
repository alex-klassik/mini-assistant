# M11 — ручная проверка OutlookMailChannel на живом Outlook

`OutlookMailChannel` управляет реальным COM-объектом Outlook через JACOB.
Такой код нельзя честно покрыть юнит-тестом: в CI нет ни установленного
Outlook, ни нативной `jacob-1.20-x64.dll`, ни живого почтового ящика — это
не имитируемая (mockable) зависимость, а фактическое внешнее приложение
операционной системы. Поэтому вместо `mvn test` здесь — чек-лист ручных
шагов, которые нужно один раз пройти на машине с установленным и открытым
Outlook перед защитой задания.

## Предусловия

- Windows, установлен классический Outlook (desktop, не new Outlook /
  Outlook Web), пользователь залогинен в свой почтовый профиль.
- Outlook запущен и уже открыт (проще всего подключиться к работающей
  сессии, чем поднимать новую).
- `jacob-1.20-x64.dll` лежит на `PATH` (или рядом с исполняемым jar) — без
  неё `new ActiveXComponent("Outlook.Application")` упадёт с
  `UnsatisfiedLinkError`.
- Java 8 (x64, должна совпадать разрядность с `jacob-1.20-x64.dll`).

## Шаг 1 — fetchUnread() видит непрочитанные письма

1. В своём почтовом ящике убедиться, что во «Входящих» есть хотя бы одно
   непрочитанное письмо (или создать тестовое, отправив себе).
2. Написать/запустить небольшой ad-hoc сценарий (или дождаться M13, где это
   будет частью `Main`), который создаёт `new OutlookMailChannel(null, null)`
   и печатает результат `fetchUnread()` (id, отправитель, тема, длина тела).
3. **Ожидаемо:** в списке присутствует именно то письмо, которое было
   непрочитанным; поля `from`/`subject`/`body` соответствуют реальному
   содержимому письма, `id` — непустая строка (Outlook `EntryID`).
4. Отметить письмо как прочитанное вручную в Outlook и повторить вызов
   `fetchUnread()` — письмо **не должно** больше входить в список
   (реализация фильтрует по `[UnRead] = true` на стороне Outlook).

## Шаг 2 — reply() реально отправляет ответ

1. Взять `Msg`, полученный на шаге 1 (или новое непрочитанное письмо).
2. Вызвать `outlookMailChannel.reply(msg, "Тестовый ответ от ассистента")`.
3. **Ожидаемо:** в папке «Отправленные» появляется новое письмо-ответ на
   исходное (тема с префиксом `RE:`, получатель — исходный отправитель),
   с телом `"Тестовый ответ от ассистента"`.
4. Проверить у себя (или у второго тестового ящика, если переписка была
   между двумя реальными адресами), что письмо действительно дошло.

## Шаг 3 — параметр folder (опционально, если используется не Inbox)

1. Создать в Outlook подпапку внутри «Входящих», например `AssistantTest`,
   и переместить туда одно непрочитанное письмо.
2. Создать `new OutlookMailChannel(null, "AssistantTest")`.
3. **Ожидаемо:** `fetchUnread()` возвращает письмо из `AssistantTest`, а не
   из корневых «Входящих».

## Шаг 4 — устойчивость к отсутствию Outlook (негативная проверка)

1. Закрыть Outlook полностью (включая фоновый процесс `OUTLOOK.EXE` в
   диспетчере задач).
2. Попробовать создать `new OutlookMailChannel(null, null)`.
3. **Ожидаемо:** COM либо запускает новый процесс Outlook автоматически
   (штатное поведение `ActiveXComponent` для зарегистрированного ProgID),
   либо бросает понятное исключение из JACOB — в любом случае процесс
   ассистента не должен зависнуть без диагностики.

## Известные ограничения (зафиксировано сознательно, не баг)

- `SenderEmailAddress` для писем, пришедших через Exchange-сервер, может
  вернуть не SMTP-адрес, а Exchange Legacy DN (строка вида
  `/O=.../CN=RECIPIENTS/CN=...`) — это особенность самого Outlook COM API,
  а не нашей реализации. Для целей задания (ответ через `Reply()` на то же
  письмо) это не мешает: `Reply()` сам знает настоящего получателя.
- `reply()` полностью заменяет тело письма-ответа текстом ассистента, не
  сохраняя цитату исходного письма снизу — так проще и предсказуемее для
  разбора модели тестировщиком; штатная цитата Outlook (`>` с оригиналом)
  сознательно не добавляется в M11.
- Идемпотентность (не отвечать дважды на одно и то же письмо) обеспечивает
  `SeenStore`, а не `OutlookMailChannel` — см. Javadoc класса.
