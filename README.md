# mini-assistant

Mini-ассистент по образу «Коли»: читает непрочитанную почту через Outlook
(JACOB), обрабатывает запрос через LLM с tool-calling, отвечает письмом.
Разработан по плану из [PLAN.md](PLAN.md) — Plan-first + TDD, атомарные
коммиты (история коммитов сама по себе является частью отчёта: каждый
`test:`/`feat:` — отдельный red→green шаг).

## Сборка (build)

Нужны JDK 8 и Maven 3.6+.

```bash
mvn clean package
```

Собирает fat-jar `target/mini-assistant.jar` (все зависимости внутри,
`maven-shade-plugin`, точка входа `com.miniassistant.app.Main`).
`net.sf.jacob-project:jacob` (Java-классы COM-моста к Outlook) тянется в
jar как обычная зависимость — нативная `jacob-1.20-x64.dll` в артефакт не
входит и должна быть отдельно установлена на `PATH` окружения, где jar
запускается (см. «Запуск» ниже).

## Запуск (run)

1. Скопировать `config.example.yaml` в `config.yaml` и заполнить реальными
   значениями (`llm.endpoint`/`llm.model`, `mail.profile`/`mail.folder`,
   `store.path`). `config.yaml` — в `.gitignore`, в git не попадает.
2. Задать переменные окружения с именами, указанными в `config.yaml`:
   - `LLM_API_KEY` (или как названо в `llm.apiKeyEnv`) — ключ LLM-провайдера,
     совместимого с OpenAI Chat Completions.
   - `AUDIT_HMAC_KEY` (или как названо в `audit.hmacKeyEnv`) — секрет для
     HMAC-цепочки аудит-журнала.

   Секреты нигде, кроме переменных окружения, не хранятся и не логируются
   (см. `docs/M15-security-review.md`).
3. Предусловия для реального запуска: Windows, установленный и открытый
   классический Outlook (desktop), пользователь залогинен в почтовый
   профиль, `jacob-1.20-x64.dll` на `PATH`, разрядность JVM/dll совпадает
   (подробности — `docs/M11-outlook-manual-checklist.md`).
4. Запуск:

   ```bash
   java -jar target/mini-assistant.jar config.yaml
   ```

   Без аргумента или с несуществующим путём к конфигу процесс печатает
   понятное сообщение и завершается с ненулевым кодом, без сырого
   стектрейса — так же, как и при любой другой фатальной ошибке (см.
   `Main.main`). Процесс опрашивает почту с периодом `mail.pollSeconds`,
   на каждое непрочитанное письмо прогоняет LLM tool-loop и отвечает;
   останавливается по Ctrl+C (graceful shutdown, COM-ресурсы Outlook
   освобождаются).

## Тесты (test)

```bash
mvn test
```

52 юнит-теста, зелёные **без Outlook** (JACOB исключён из test-classpath
через `maven-surefire-plugin`/`classpathDependencyExcludes` — иначе его
статический инициализатор роняет JVM на не-Windows/CI). Покрыто по
компонентам: конфиг, tool-loop и инструменты, `AgentService`
(идемпотентность, graceful-фолбэки на сбой LLM/отправки), аудит-журнал
(HMAC-цепочка), `PiiMasker`, `SeenStore`, `HttpLlmClient` (через
`MockWebServer`), сборка `Main.buildAgentService`.

Что принципиально не покрыто автотестами (живые внешние зависимости —
Outlook COM, реальный `Thread.sleep`-цикл, `System.exit`) — заменено
ручными чек-листами и/или живым смоук-запуском:

- `docs/M11-outlook-manual-checklist.md` — `OutlookMailChannel` на живом Outlook.
- `docs/M13-main-manual-checklist.md` — `Main`/`pollLoop`/graceful shutdown.
- `docs/M15-security-review.md` — само-ревью безопасности (секреты, ПДн в
  логах, инъекции через аргументы инструментов).

## Как я работал с ИИ

Всю разработку вёл в паре с Claude Code (модель Claude Sonnet 5), в роли
не «генератора кода по запросу», а инженера, работающего по тем же
правилам, что я задал бы себе или коллеге. В самом начале я явно
зафиксировал границы этой работы и требовал их соблюдения на каждом шаге:

1. Не скорость, а безупречный результат и строгие инженерные стандарты;
   экономия токенов там, где это не в ущерб качеству.
2. Строгий **Plan-first**: сначала детальный план в `PLAN.md`, ни одного
   куска продакшн-кода без него.
3. **TDD** везде, где технически возможно: сначала падающий тест (red),
   потом реализация (green) — отдельными коммитами.
4. Итеративность: небольшие атомарные логические шаги вместо
   «AI-dump»-коммитов на много файлов сразу.
5. Безопасность по умолчанию: ПДн никогда не в логах, секреты — только из
   переменных окружения.
6. Объяснение простым языком каждого архитектурного решения и куска кода —
   мне было важно не просто получить рабочий результат, а разобраться в
   нём достаточно, чтобы защитить его.

Разработка шла по вехам `PLAN.md` (M0–M16), и каждую следующую веху я
запускал явно, прочитав и приняв результат предыдущей — ни одна веха не
стартовала без моего подтверждения.

**Что проверял у модели, а не принимал на слово.** Ключевое правило,
которое я соблюдал: не считать шаг завершённым по одному только
утверждению модели «готово», а требовать реальный запуск и реальный
вывод. Это принесло конкретный результат на M14: вместо того чтобы
остановиться на «`mvn package` собрался, значит всё в порядке», я попросил
по-настоящему запустить получившийся fat-jar с несколькими вариантами
входных данных. На одном из запусков (без установленного Outlook на
машине разработки) наружу утёк **сырой стектрейс** —
`UnsatisfiedLinkError` из JACOB не ловился объявленным в `Main`
`catch (RuntimeException e)`, потому что `Error` не является
`RuntimeException` в иерархии исключений Java. Это прямо противоречило
собственной документированной цели класса — никогда не показывать сырой
стектрейс на фатальной ошибке. Я потребовал это исправить (расширить
`catch` до `Throwable`), перепроверить тем же самым сценарием и оформить
отдельным `fix:`-коммитом, не смешивая с плановой веткой M13/M14 — именно
такую находку и должна вскрывать проверка «перед завершением», а не
проверка «код компилируется».

Второй проверочный контур — отдельная веха M15, где по моему запросу
модель прогнала (и я перепроверил результаты) grep по коду и **всей**
git-истории на секреты, построчный аудит каждого вызова логирования на
предмет тела письма/ПДн, и разбор того, как аргументы инструментов
(`add_reminder`/`find_items`) попадают в файловую систему — чтобы
исключить путь, при котором содержимое письма или ответ модели могли бы
повлиять на то, какой файл на диске читается или пишется. Результат
зафиксирован в `docs/M15-security-review.md`.

**Что я отклонял/менял.** Самое существенное отклонение — от самого
формата работы, который модель предложила бы по умолчанию: не «сгенерировать
весь проект целиком за один проход», а вести его вехами с обязательной
паузой на моё подтверждение и раздельными red/green-коммитами — так,
чтобы каждый шаг можно было независимо прочитать, понять и при
необходимости отклонить до того, как на него наслоится следующий. Там, где
честный юнит-тест был технически невозможен (живые COM-объекты Outlook в
M11, `main()`/бесконечный poll-loop в M13, сборка jar в M14) — я не
принял вариант «просто не тестировать это», а потребовал заменить
формальный тест ручным чек-листом с чёткими шагами и ожидаемым
результатом, которые можно пройти на реальной машине.

## Экспорт сессии Claude Code

Полная стенограмма работы с Claude Code по этому заданию — в
`docs/claude-code-session-export.md` (сгенерирована разбором сырого
JSONL-лога сессии; внутренние блоки рассуждений модели опущены, объёмные
результаты команд и содержимое записываемых файлов обрезаны — полный текст
файлов см. в самом репозитории; реальные имя и корпоративный email автора,
однажды прозвучавшие в переписке, замаскированы. Места автоматического
сжатия истории диалога (compaction) в самой сессии отмечены отдельной
пометкой прямо в тексте экспорта).
